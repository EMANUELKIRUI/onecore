# Module architecture

Each future business module is independently structured with `domain/`, `application/`, `infrastructure/`, `api/`, `ui/`, `configuration/`, `permissions/`, `workflows/`, `tests/`, `module.manifest.ts`, and `README.md`.

The canonical manifest is validated in `@onecore/core-domain` and includes module identity, semantic version, display name, dependency names and optional minimum versions, canonical permissions, feature keys, lifecycle, and optional configuration/metadata. The registry reuses `modules`, `module_versions`, `module_dependencies`, `module_permissions`, and `features`. Its lifecycle progresses through development, testing, review, approval, availability, deprecation, and retirement; only `AVAILABLE` modules can be newly requested or enabled.

Organization-specific state remains in the RLS-protected `organization_modules` table. Activation requires an active subscription/plan entitlement, an available module, and enabled dependencies. The Phase 5 authorization service resolves those requirements before a permission is effective. Module requests, enables, and disables are organization-authorized and audited; dependent modules prevent disabling a required module. Global catalog registration and lifecycle updates are restricted to the trusted registry service using a live platform-superadmin session and privileged provisioning connection. See [module entitlement security](../security/module-entitlements.md) and [ADR 0007](../architecture/adr/0007-module-registry-and-entitlements.md).

Modules own their domain rules. They integrate through versioned contracts and internal events, not direct access to another module's internals or tables. The core Business Manager capability currently provides organization-scoped customer and product/service catalog master data only. No customer-specific module implementations or downstream business transactions have been added. POS, Inventory, Sales, Finance, HR, School, Healthcare, Hotel, AI, and other business modules remain out of scope.
